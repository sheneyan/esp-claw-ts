# N16R8 SSD1306 OLED Probe: Implementation Plan

> **Scope:** prove the four-wire I2C OLED connection only. This is deliberately
> not an OLED user interface, key-input implementation, TF-card feature, or a
> change to ESP-Claw's existing FATFS content.

## Preconditions and invariants

- Target: ESP32-S3 N16R8 TS-Claw board on `/dev/cu.usbmodem5C930635061`.
- Wiring already made: `GND -> GND`, `VCC -> 3V3`, `SCL -> GPIO5`,
  `SDA -> GPIO4`. Do not connect the four key wires in this slice.
- Build with `/Users/sheneyan/esp/esp-idf-v5.5.4`; do not use IDF 6.
- The board's current `/fatfs` contains live configuration and data. Default
  `idf.py flash` is unsafe here because its flasher arguments include
  `system.bin` and `storage.bin`. Do not run it.
- No partition-table, NVS, OTA-data, system-FATFS, storage-FATFS, Wi-Fi,
  Tailscale, provisioning, or Exit Node setting may be written by this work.

## Intended behavior

After board-manager initialization, the app obtains one shared I2C master
named `oled_i2c`, probes only addresses `0x3C` then `0x3D`, and—when one ACKs—
initializes a 128x64 SSD1306 and renders a compact static diagnostic screen
(`ESP-CLAW`, `OLED OK`, and the detected address). Failure to obtain the bus,
an absent display, or an I2C transaction error is logged and is non-fatal:
Wi-Fi, Tailscale, web chat, FATFS, and the provisioning button continue.

## File plan

### 1. Describe the physical I2C bus in the board profile

Modify `application/edge_agent/boards/local/esp32_s3_n16r8_ts_claw/board_peripherals.yaml`.

- Add a single board-managed I2C-master peripheral named `oled_i2c` using port
  0, SDA GPIO4, SCL GPIO5, 100 kHz, and the board-manager's normal I2C schema.
- Keep existing `rmt_tx` GPIO38 unchanged.
- Do not add key GPIOs or any SD/SPI bus now.

**Check:** regenerate the board-manager configuration and inspect the generated
I2C configuration before compiling. This proves that the YAML schema is valid;
it does not prove the panel is connected.

### 2. Add a tiny, standalone non-fatal probe component

Create `application/edge_agent/components/oled_probe/`:

- `CMakeLists.txt`: register the component and depend on `esp_board_manager`,
  `esp_driver_i2c`, and `log` only.
- `include/oled_probe.h`: expose `esp_err_t oled_probe_start(void)` and a
  small pure helper interface used by host tests.
- `oled_probe.c`: reference `oled_i2c` through
  `esp_board_periph_ref_handle()` rather than constructing another I2C bus;
  probe `0x3C`, then `0x3D`, with bounded 100-ms transfers. On success send a
  conventional SSD1306 128x64 initialization sequence and a 1 KiB page
  framebuffer. On every unsuccessful path, release a referenced bus and
  return an error for the caller to log.
- `oled_probe_render.c`: build the static 128x64 monochrome framebuffer from a
  minimal embedded glyph table. It must not allocate from a hot loop, create
  tasks, or poll the display repeatedly.

The component sends the SSD1306 control bytes directly over I2C (`0x00` for
commands, `0x40` for display bytes); it does not add LVGL, a display service,
or a third-party panel component for this one-screen diagnostic.

### 3. Make startup best-effort and board-scoped

Modify `application/edge_agent/main/main.c` and its CMake requirements.

- For `CONFIG_ESP_BOARD_ESP32_S3_N16R8_TS_CLAW` only, call
  `oled_probe_start()` immediately after `esp_board_manager_init()`.
- Log success including the detected I2C address. Log failure at warning level
  and continue; never wrap it in `ESP_ERROR_CHECK`.
- Add `oled_probe` to the main component's conditional private requirements.
- Leave `CONFIG_APP_CLAW_LUA_MODULE_LCD=n` unchanged: this is a probe, not a
  general display/Lua UI feature.

### 4. Tests before target build

Create host-side tests under `application/edge_agent/components/oled_probe/test/`.

- Address-selection tests: select `0x3C` when both ACK; select `0x3D` only
  when `0x3C` fails; report no address when neither ACKs.
- Renderer tests: output is exactly 1024 bytes; it is not an all-zero buffer;
  the expected rows change for the detected-address field; a second render is
  byte-identical.
- Keep I2C transport behind a narrow wrapper so host tests do not need an
  ESP-IDF device driver or a real panel.

Run the host tests first. Then regenerate board-manager artifacts and perform
the regular IDF 5.5.4 target build. No build command may flash the device.

## Safe physical verification sequence

1. Stop and inspect the current port and tailnet status. If the target port or
   MAC differs, do not flash.
2. Create a **full 16 MiB read-only backup** outside the Git repository with
   `esptool.py read_flash`; SHA-256 it and restrict the backup file to the
   local user. Do not print its contents or commit it.
3. Build only using IDF 5.5.4:
   `idf.py gen-bmgr-config -b esp32_s3_n16r8_ts_claw -c boards/local`, then
   `idf.py build`.
4. Compare `build/flasher_args.json` against the safe procedure. Do **not**
   invoke it. Flash only `build/edge_agent.bin` at offset `0x20000` with
   `esptool.py write_flash`; this touches only the active app-partition range.
   It must not include `storage.bin`, `system.bin`, NVS, OTA data, partition
   table, `erase_flash`, or a format command.
5. Let the board reboot. Verify in this order:
   - serial logs show `OLED` probe result (ACK address or non-fatal absence);
   - user visually confirms the OLED's static screen;
   - `/api/status` still returns Wi-Fi and `/fatfs` storage;
   - `tailscale ping esp-claw` still reaches the board.
6. If the screen does not work, stop after capturing the one boot log and the
   observed screen state. Do not change pins, flash again, or attach keys
   without a new hypothesis and user confirmation.

## Acceptance criteria

- Host tests and IDF 5.5.4 build pass.
- With the presently wired SSD1306, the screen visibly shows the static probe
  screen and logs the address used (`0x3C` or `0x3D`).
- The board remains reachable over its existing Tailscale identity and status
  API, and its FATFS-backed configuration remains present.
- With the OLED unplugged, boot continues and all existing TS-Claw services
  stay available.
- No key, TF, Taildrop, or generic OLED UI promise is made by this change.
